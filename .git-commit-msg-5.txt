Catalog Intelligence runs: reliable Stop, self-healing, exact progress

A Premium run died at row 6/25 and Stop did nothing: the orchestrator's
process was gone, Stop only set a flag for it to read, and the sweep that
should recover dead runs had returned 503 on every call because the app
env var it needed was missing. This hardens the whole run lifecycle.

Stop
- Stop starts no new row. Rows already with the AI finish (a research
  loop is told to answer at its next round), are saved and charged, then
  the run ends cancelled. In-flight OpenAI calls are no longer aborted,
  which used to pay for results and throw them away.
- If the orchestrator is already dead, Stop finishes the run immediately
  from what is actually saved.

Dead-worker recovery
- The orchestrator pings its heartbeat every 30s for as long as its
  process lives, so a 2.5-minute-old heartbeat reliably means dead, never
  a slow row.
- The status poll, Start, and the sweep all recover a dead run: resume it
  from the last saved row, or finish it if Stop was pressed. An atomic
  claim means only one caller ever re-dispatches.
- Worker fencing (job_runs.worker_token): every orchestrator start owns
  the run under a fresh token; heartbeat, progress and final writes only
  land for the owner, so two workers can never double-process, clobber
  each other, or finish the same run.
- The sweep now authenticates against the Vault secret pg_cron already
  sends (verify_jobs_cron_secret, service_role only), so recovery works
  without the missing env var.

Accuracy
- Each finished row's id is recorded in the same write as its result, so
  a resume never re-processes (or has OpenAI bill) a finished row.
- Progress = rows this run processed and saved, by saved status — the
  same count the server uses to close the run. Fixes a regression where
  re-running already-done rows (e.g. Premium retry of Not found) showed
  100% at once.
- One row that throws becomes a failed row instead of killing the run;
  result and charge writes retry on transient database errors.

Frontend
- One poll loop that never dies: network drops and 5xx (e.g. mid-deploy)
  back off and retry instead of freezing the bar.
- Returning to the tab, regaining focus, or coming back online refreshes
  at once; "Stopping..." stays accurate after a reload.

Verified: tsc clean, eslint clean on every touched file (sidebar.tsx at
its baseline), 251/251 vitest tests pass including new Stop, fencing,
resume, row-isolation and recovery tests, and next build compiles.
